TIMELINE
SR 48000. BEAT = 24000 samples (120 BPM). L = take length in samples. t0 = 1000 is the arm sample. n is the sample index.
rec = 1 on [t0, relAt). finishreq = 1 on the single sample finAt. finishtarget = L unless stated.
Expected loop for a take of length L: E(t) = x[t0 + ((t - t0) mod L)].
Window W(L) = [t0+L+1, t0+4L+1): three full periods after recording stops.

SCENARIOS (the DSP depends on master length, so every check names its scenario)
A: session master, M = 6 beats = 144000 samples, B = recordedBeats = 6.
B: self master, M = L, B = L/24000.
P: phrase master, M = 16 beats = 384000 samples, B = 16.

CHECK 1 - seamless wrap
Takes N in {1, 2, 3.5, 6} beats, so L = 24000, 48000, 84000, 144000. Scenarios A and B. finAt = t0 + floor(L/2), relAt = finAt + 1, finishtarget = L. Run length t0 + 4L + 16.
Pass per (scenario, take), both required:
(a) zero mismatches between y(t) and E(t) over W. Exact float32 equality; no tolerance.
(b) wrap step rule: for every wrap sample w in W (w with (w - t0) mod L = 0), |y(w) - y(w-1)| <= max |y(t) - y(t-1)| over the other samples t in W with t > W.start.
CHECK 1 PASS iff all 8 (scenario, take) pairs pass.
Reading: "sample-exact" means zero mismatches. "Stop point" is the playback wrap at the take length. If the DSP wraps at any other length (for example grid snapping), the samples disagree and the pair FAILS. Effective wraplen min and max over W are reported as diagnostics, not as pass criteria.

CHECK 2 - early press keeps recording to target
L = 2 beats (48000), scenario A, finishtarget = L, early press at E in {12000, 47999}, finAt = t0 + E, rec held on [t0, finAt+1). Run length t0 + L + 10.
Criterion: writeidx(t) == min(t - t0, L) for every t in [t0, t0+L+2], zero mismatches. Reading: the write index advances by 1 each sample while widx < finishtarget, and holds at L afterwards.
Control (harness validity only): same take with no finishreq and rec held on [t0, t0+E+1). Criterion: writeidx is constant on [t0+E+2, end). If the control fails, check 2 is INCONCLUSIVE, not PASS.
CHECK 2 PASS iff both E values pass the criterion and the control is valid.

CHECK 3 - read offset latencybias = N
L = 2 beats (48000). Scenarios A (M = 144000, B = 6) and B (M = 48000, B = 2). finAt = t0 + L/2, relAt = finAt + 1, finishtarget = L. Run length t0 + 4L + 512.
Reference run R at latencybias 0. Test run O at latencybias N, N in {64, 259}.
Reading of "shift by N": a positive latencybias advances the read position, so the expected output is O(t) = R(t + N), with R taken periodically at period L. The sign is fixed: O(t) = R(t - N) is a FAIL.
Pass per (scenario, N), all required:
(a) zero mismatches between O(t) and R(t+N) over W.
(b) O(t) == R(t) for every t < t0 + L + 1 (recording region; nothing else changes).
(c) writeidx and wraplen identical between O and R for every t in the run.
CHECK 3 PASS iff all 4 (scenario, N) pairs pass.

CHECK 4 - fold ladder
Phrase P = 16 beats (scenario P). Takes L = P/2^k for k in {1, 2, 3, 4}, so 8, 4, 2, 1 beats. foldNow F in {0, 1}, held constant for the run. finAt = t0 + L/2, relAt = finAt + 1, finishtarget = L. Run length t0 + 4L + 16.
Pass per (k, F), both required:
(a) wraplen(t) == L for every t in W.
(b) zero mismatches between y(t) and E(t) over W.
CHECK 4 PASS iff all 8 (k, F) pairs pass.

VERDICT RULES
PASS only if every criterion of the check holds with the exact numbers above.
FAIL if any criterion fails. No tolerance: any nonzero mismatch count fails.
INCONCLUSIVE if harness validation fails: a control path is missing, the loop.dsp sha differs, the input or output counts differ, or the check 2 control is invalid.
Every run is reported as measured. Failing rows are reported, not dropped.

AMENDMENT 1 - backend (dated 2026-10-24, committed before any render on this route)
Peer 420 decided that verdicts come from the C++ backend with the pinned flags. The LLVM JIT route written above (createDSPFactoryFromFile) is comparison only and produces no verdicts. Kernel heclgang/loop-witness-run version 2 did not compile anything: its guard stopped on the sha, which the correction in commit cede992b fixed.
Compile route for verdicts: libfaust 2.85.9 from the release zip libfaust-ubuntu-x86_64.zip. faust_cli is the faust 2.85.9 entry point, createFactory from compiler/main.cpp, linked against lib/libfaustwithllvm.a with the plain recipe (g++ -O2 -std=c++17, -lz -lpthread -ldl -lm -ltinfo). It runs as `faust_cli -lang cpp -vec -fun -dfs -vs 32 -nvi -ct 0 -I <faustlibraries> loop.dsp -o dsp.cpp`. The generated class is mydsp.
Faust libraries: github grame-cncm/faustlibraries at 78a72d4998dec43e20492ef9b78d1a785b3dc864. Architecture headers: faust 2.85.9 source tarball, architecture/.
Harness build: g++ -O3 -std=c++17 -I <faust 2.85.9 architecture> loop_witness.cpp, with no -mcpu. The harness includes dsp.cpp and drives mydsp through MapUI with the same control paths and per-sample scheduling as above.
The flag-check route's render_cpp driver is a wav renderer with no control inputs, so the four checks cannot use it. The harness uses the same generated class and compile flags.
Thresholds, scenarios, timelines, expected-loop definition, and criteria are unchanged.
